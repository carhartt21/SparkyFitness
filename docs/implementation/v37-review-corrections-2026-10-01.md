This batch addresses the seven v37 review findings and the owner's clarified weekly-planning requirement. The baseline is the shipped v37 source, `663895d8c`. Work takes place on `feat/v37-corrections-20261001`; unrelated worktrees and draft features remain intact.

**Execution update, 2026-10-02:** the verified batch was merged to `main` as `899ac67bc` and deployed to the private production server. Mobile build/upload and Apple availability are separate release states, recorded in the private release package. The original release sequence below is retained as the plan at review time; it is not a pending merge instruction. Current usage is documented in [Weekly training plans](../src/features/exercises/weekly-planning.md), [MCP-based training](../src/features/exercises/mcp-training.md) and [Notifications](../src/features/settings/notifications.md).

## Stage 1 — Save integrity and the database correction

1. Guard explicit check-in completion/skip before asynchronous navigation. Prevent duplicate taps and ensure a failed save retains editable answers. Test immediate `beforeRemove`, back-to-save, failure/retry and day changes.
2. Replace the incorrect workout-history owner foreign key through a new migration rather than changing an applied migration. Fail visibly on inconsistent history instead of deleting records. Preserve existing policies and sharing boundaries.
3. Make web plan dialogs await their mutations, retain input on failure, disable repeated submission and close only after success. Remove routine logging of full plan payloads.

## Stage 2 — Activity-first weekly planning

1. Extend the existing assignment model and shared request/response contracts with a bounded activity identity, optional session label, local time, duration and distance. Validate mutually exclusive activity/preset/exercise identities, numeric bounds, schedule days and ownership. Existing assignments and sequential plans remain readable.
2. Update repository round trips and immutable history snapshots. Keep planned activities separate from completed exercise entries and never credit activity energy merely for a plan.
3. Build an activity-first web editor and mobile week view/editor using existing navigation, presets, queries and services. Support several sessions on one day, optional sessions/rest, active date ranges and existing advanced set editing. Reuse logging flows and carry the originating assignment identity through completion.
4. Invalidate plan lists, active plans, history, daily progress and diary summaries consistently after mutations. Handle unavailable network access without pretending a plan was saved.

## Stage 3 — Accurate and actionable daily progress

1. Derive configured objectives and scheduled sessions from existing persisted state, with no aggregate health score or invented target. A configured dose is not a confirmed intake; a scheduled session is not a completed workout; unknown nutrition is not zero.
2. Mark import-only meal groups explicitly using importer provenance. Preserve imported diary snapshots and their historical visibility; do not infer category purpose from arbitrary user-entered names.
3. Carry reference identifiers into meal, habit, measurement, intake and workout destinations. Translate system meal labels while leaving custom labels literal.
4. Present one restrained Progress X completion overlay on a real incomplete-to-complete transition with a meaningful denominator. Respect reduced motion, decreases, past days and repeated renders.

## Stage 4 — Freshness, keyboard and German UI correction

1. Refresh caffeine on screen focus and app foreground, update its clock promptly, and invalidate dates affected by food/supplement edits. Retain the intentional residual model; distinguish dose dates in multi-day charts.
2. Use a shared keyboard action row with translated dismissal/save labels, adequate targets and correct safe-area handling. Check quantity, servings and intake forms, including rapid input and dismissal.
3. Correct English source/reviewed German overlays together. Inspect the affected headers, settings descriptions, meal names, fasting labels, accessibility text and errors. Run the overlay check and localization checks.

## Stage 5 — Review, integration and release

1. Run focused server tests for changed contracts, repository/service behavior and migrations; skip the full backend suite as requested. Run affected mobile/web tests, package validate wrappers and builds, then the full mobile/web suites where shared navigation/contracts warrant them.
2. Rehearse migrations in an isolated synthetic database, including upgrade, preserved history and owner/sharing behavior; boot the server normally. Never use production records as test fixtures or hand-edit the schema snapshot.
3. Render synthetic web/mobile states where tooling permits. Review German copy, narrow layouts, keyboard actions, loading/empty/error states and the new planner. Correct findings and repeat the affected checks. Record unavailable physical-device checks as unverified.
4. Commit reviewable stages. Compare the final branch against current main/origin, resolve integration issues, merge and push only after the release gates pass.
5. Publish the exact merged source through the TestFlight runbook and deploy production in parallel. Use a fresh encrypted backup, retained images/compose rollback, clean source archive, health/API checks and release records. Confirm upload acceptance without submitting the same binary twice.

## Plan review and adjustments

The plan was reviewed against the repository checklist. The database repair precedes planner UI work because it is the observed creation blocker. Whole-activity planning extends the existing workout domain rather than the unrelated draft activity-goal branch. Progress follows persisted evidence and reference identities; it does not add a scheduler, outbox, score or calorie policy. Database, shared contracts, both consumers, localization and migration/security documentation are included in the same batch. Release is authorized, but remains gated on the checks above.

## Execution evidence

Stages 1–4 are implemented. The self-review added three corrections: decimal-comma quantities remain editable until save; adding a whole activity to a legacy prefill plan switches it to prompt mode; objective navigation retains the selected date and hydration opens the existing ledger. The web dialog cannot close through Cancel while a save is pending. No planned assignment writes completed exercise or calorie data.

### Remaining verification and release

Physical iPhone/Watch logging, notification delivery, HealthKit writeback and offline saves after process termination were not exercised in this batch. The existing calendar's weekday labels at extreme text enlargement remain a separate layout limitation. Long editor titles truncate visually while their accessible labels and the Save action remain available. A completion overlay's real-device animation is unverified; its scalar/evidence and reduced-motion handling reuse the established Progress X component.

The clean tested branch is to be merged with the already shipped v37 ancestry, then published from the exact merged revision. Production uses only the three rehearsed migrations, a matched encrypted backup verified off-host, retained images and configuration, and checks for unchanged routing, mounts, BLS count and owner policies. Image rollback does not reverse additive database migrations. Deployment and mobile publication run concurrently; their private release package records actual build/upload status and deployed image revisions separately. A queued build is never reported as available in TestFlight.
