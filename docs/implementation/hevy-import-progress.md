# Stage 3 Hevy import progress

This records implementation against the [six-stage plan](https://app.notion.com/p/3e55fb777c5d811eb71ce24de890c803). Physical and real-account validation stays in [physical-device-tests.md](./physical-device-tests.md). The user supplied an authorized completed-workout CSV in chat; it is not stored in the repository. Tests use synthetic data.

## Implemented

- Settings → Data Import offers a dry run of Hevy completed-workout CSV with workout and set-row counts, workout names/times, exercise counts, exact previously imported source matches, exact exercise-name library matches, and same-day/same-title session overlap warnings. Overlaps are review candidates, never automatic merges; the import screen requires an explicit acknowledgment when they appear. The dry run writes no diary data. Import requires a reviewed IANA timezone because the CSV timestamps have no UTC offset; nonexistent and ambiguous local times fail rather than being guessed.
- The parser retains set order, warm-up and drop-set types, weightless bodyweight sets, durations, distance, RPE, notes, supersets, and repeated exercise occurrences. Exact repeated source rows are flagged by their CSV row numbers and retained; a warning alone never removes a possibly legitimate set.
- Completed workouts use stable CSV source IDs. Re-import skips existing source IDs and preserves local edits. The API integration separately imports saved routines by their Hevy IDs, rather than deriving a routine from a completed workout with a familiar title. The CSV does not include saved routines.
- The web importer shows partial failures and permits retry from the same file. Synthetic server and web tests cover parser boundaries, duplicate warnings, preview visibility, timezone validation, and retry behavior.
- Library → Exercise review on the phone shows Monday-based calendar weeks, calendar months, and calendar years, with explicit prior-period dates and overall/running/cycling/strength/other session summaries. The current unfinished period compares against the same elapsed part of the prior calendar period, capped at its end when it is shorter (for example, March 1–30 versus February 1–28). Earlier selected periods compare complete calendar periods. The device supplies its local calendar day; the API accepts explicit day ranges and returns those dates. The server uses provider sport details where available and labels name-inferred classifications. Distinct exercises in one preset workout count as one overall session; distance, duration, reps, and lifted volume include only recorded values. No workout energy is inferred from missing data. The response also lists each recorded session ID/date once, including grouped workouts; tapping one loads that day's existing diary summary and opens the exact workout or activity detail, where its source and recorded sets remain inspectable. Legacy local source keys display the current X on Track brand.
- The review API also returns calendar-aligned daily, weekly, or monthly sport points with empty intervals retained. The phone can switch running/cycling/strength and inspect session counts plus recorded distance or lifted volume over the chosen period, in preferred units. Future workout-plan entries are excluded until a set has an explicit completion timestamp, so merely scheduling a workout does not inflate the review. Server and phone tests cover the aggregation and sport/metric switching.
- Workout-plan edits and deletion now preserve entries with completed sets. Dated plan snapshots record the schedule at create, edit, and delete time, and generated entries retain their original assignment ID even when the live plan foreign key is cleared. The review reports scheduled slots with at least one completed set as attended, a numerator/denominator and rate, the earlier period, and the count of elapsed days with known plan history. Today is excluded. Existing plans receive a baseline on the owner's local migration day, used only when that day has elapsed; earlier plans are not reconstructed from their current state. The migration passed an isolated PostgreSQL smoke test for baseline seeding, origin backfill, deletion survival, and forgery protection; application-database migration and RLS verification remain pending. On 25 September 2026, the default local PostgreSQL socket had no server and Docker's daemon socket was absent, so the application-database check could not run in this environment. The policy file does contain report/diary-readable, owner-insert-only policies for the new version table; those still need runtime verification.
