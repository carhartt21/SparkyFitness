# Micronutrient coverage investigation and implementation plan

Date: 2026-10-01. Status: implementation started with conversion and observation contracts. Reviewed 2026-10-01 against `main` at `ce840f415`; see [Review notes](#review-notes-2026-10-01).

The missing micronutrients primarily result from narrow provider mappings and incomplete health-import contracts. The application already has a magnesium catalog entry, custom nutrient storage, and aggregation support. Expanding only the visible nutrient picker would leave the underlying data missing. The proposed work extends the existing catalog, preserves nutrient identity and units through ingestion and snapshots, and makes the resulting values available consistently in web and mobile.

## Scope and evidence limits

This investigation follows the code across shared, server, web, and mobile. The review re-checked every finding against `main` at `ce840f415`, where the packages are named `XoTServer/`, `XoTMobile/`, and `XoTFrontend/`; paths below use those names and are relative to the package unless they start with `shared/`. It does not establish which revision is deployed or whether a particular user's HealthKit store contains magnesium. No live database, production service, or device health records were inspected. Existing unrelated working-tree changes are outside this plan.

External capability checks confirm that [HealthKit supports dietary magnesium as a cumulative mass quantity](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/dietarymagnesium) and that [BLS 4.0 provides 138 components, including individual vitamin forms](https://www.blsdb.de/bls). BLS components also include macros, amino acids, fatty acids, and fiber fractions; 138 is not a count of independent micronutrients to sum together.

The BLS documentation PDF was blocked by the source site's security challenge, and the linked errata PDF could not be retrieved. Exact mappings for the additional components and the present status of the vitamin A correction therefore require verification against the official workbook and documentation during implementation. The vitamin A exclusion below is a confirmed code decision, not a independently verified claim that the current source data remain incorrect.

## Target scope: the Apple Health micronutrients

The target set is the vitamins and minerals that Apple Health can record: 27 nutrients, taken from the `HKQuantityTypeIdentifierDietary*` identifiers in the installed iOS 26.5 SDK headers and confirmed in `@kingstinct/react-native-healthkit` 15.1.0, the version `XoTMobile` pins. Macronutrients, caffeine, and water are already handled and are not part of this plan.

| Group | Already a built-in column (6) | New, stored as custom nutrients (21) |
| --- | --- | --- |
| Vitamins (13) | Vitamin A, Vitamin C | Thiamin (B1), Riboflavin (B2), Niacin (B3), Pantothenic acid (B5), Vitamin B6, Biotin (B7), Vitamin B12, Folate, Vitamin D, Vitamin E, Vitamin K |
| Minerals (14) | Calcium, Iron, Potassium, Sodium | Chloride, Chromium, Copper, Iodine, Magnesium, Manganese, Molybdenum, Phosphorus, Selenium, Zinc |

Every entry except chloride already exists in `shared/src/nutrients/micronutrientCatalog.ts`; chloride needs a new catalog entry. HealthKit stores all of these as mass quantities and accepts any mass unit, so conversion uses the catalog unit (µg for vitamins A, D, K, B12, biotin, folate, chromium, iodine, molybdenum, selenium; mg for the rest).

Out of scope for collection: choline, omega-3, EPA, DHA, and the other catalog entries that HealthKit cannot represent; BLS components outside the target set (amino acids, fatty-acid detail, fiber fractions, sugar alcohols, individual vitamin forms without a target-set equivalent); and any other provider field without a target-set mapping. Supplement entry keeps its existing catalog, including those nutrients, unchanged. Health Connect's nutrition record covers the same 27 nutrients, so Android follows the same set once its bridge capabilities are confirmed (Phase 4).

HealthKit names each nutrient without fixing a chemical form. A source value enters the target set only when its form is a documented equivalent: BLS vitamin A stays blocked as before, and the BLS manifest must state which vitamin E, folate, and niacin component (if any) maps to the target nutrient. Unmatched forms are classified as out of scope, not converted.

## Findings and root causes

| Layer | Confirmed behavior | Effect |
| --- | --- | --- |
| BLS source import | `XoTServer/scripts/import_bls4.py` validates all 138 `CODE label [unit/100g]` headers and stores numeric values, qualifiers, origins, references, and the dataset SHA-256 per food. It does not store the units: they exist only in the workbook headers. | The importer retains the broader source dataset, but a unit-aware mapping needs the header units captured in the Phase 1 manifest. The inspected code does not demonstrate what is loaded in any running database. |
| BLS normalization | `XoTServer/integrations/bls/blsFoodService.ts:mapBlsFood` exposes four core fields and eleven optional fields. It never emits `provider_nutrients`, `provider_nutrient_units`, or `custom_nutrients`. The v2 search and detail routes already run `enrichWithCustomNutrients` on BLS results. | Only 15 of the 138 components reach the normalized food. Magnesium and most vitamins/minerals disappear before saving or displaying a result. Emitting `provider_nutrients` would immediately reach the existing (flawed, see below) matcher. |
| BLS vitamin A | The mapper explicitly omits vitamin A pending corrected errata values. | This is a separate deliberate exclusion that needs a source-version decision. |
| Nutrient storage | `shared/src/constants/foodVariantNutrients.ts` defines a fixed nutrient list. `FoodVariants.zod.ts` and `FoodEntries.zod.ts` also support `custom_nutrients`. | Magnesium lacks a dedicated column, but the database model can already carry it through custom nutrients. |
| Shared catalog | `shared/src/nutrients/micronutrientCatalog.ts` already has stable `id`s, a typed `unit` (`g`, `mg`, `µg`, `IU`), FDA label Daily Values as `rdi`, `aliases`, a `fixedField` link for nutrients that are built-in columns (vitamin A/C, calcium, iron, potassium, sodium, …), and `components` for compound picker entries (omega-3 → EPA + DHA). `XoTServer/services/customNutrientService.ts:ensureCatalogNutrients` resolves `fixedField` entries to their column and otherwise creates a definition with the RDI as a goal target and the supplement view groups. | Identity, units, and a first relationship field exist; they need extending, not inventing. `components` means "enter each part separately" in the supplement picker, not an aggregate/part summing rule. The catalog is not wired into food or health adapters, and its provisioning seeds goals as a side effect. |
| General provider enrichment | `XoTServer/routes/v2/foodRoutes.ts:enrichWithCustomNutrients` matches transient provider fields to existing user nutrient names/aliases through `XoTServer/utils/foodUtils.ts`, converting with `shared/src/utils/nutrientMatching.ts:convertNutrientAmount`. When conversion returns `null` (missing provider unit, unknown unit, IU, cross-family), `foodUtils.ts` stores the unconverted value. The shared unit normalizer maps `ug`/`mcg` to `µg` but not the Greek letter `μ` (U+03BC). | Support depends on prior user setup and the adapter emitting the fields. BLS does neither automatically. Adding a custom Magnesium nutrient alone does not fix BLS, and a unit mismatch can silently store a value off by a factor of 1,000. |
| HealthKit mapping | `XoTMobile/src/services/healthkit/writebackMappers.ts` builds its dietary map from `HC_NUTRIENT_COLUMNS`, then restricts it to a fixed HealthKit identifier list. Read transformation reverses that map. | Read and write agree, but both exclude magnesium and the wider micronutrient set. An Android field list effectively limits the iOS adapter. |
| HealthKit loose samples | `XoTMobile/src/services/healthkit/index.ts:readLooseNutrition` queries `DIETARY_WRITE_IDENTIFIERS`; the same list drives the permission request and probe. The transformer ignores unrecognized quantities in food correlations. | Missing nutrients are either never queried or discarded. A magnesium-only correlation can be dropped entirely because it has no recognized positive nutrient. |
| HealthKit background delivery | `XoTMobile/src/services/healthkit/backgroundDelivery.ts` observes only `DietaryEnergyConsumed` for Nutrition. | A micronutrient-only sample does not wake background sync; it waits for the next foreground or manual sync. |
| Mobile upload contract | `XoTMobile/src/types/healthRecords.ts:TransformedNutritionEntry` contains fixed fields and no additional nutrient collection. | Expanded readings have no typed transport path to the server. |
| Android parity | `XoTMobile/src/services/healthconnect/dataTransformation.ts` explicitly drops non-column nutrients such as magnesium and B12 because custom names and units are user-defined. | The same architectural gap affects Health Connect and would remain after an iOS-only fix. |
| Server health ingestion | `XoTServer/services/healthDataHandlers.ts:ingestNutritionFoodEntry` (untyped `any` parameters) builds only `NUTRITION_DIRECT_COLUMNS` and sends those to variant creation/update and diary snapshot overrides. Entries already use `serving_size = 1`, `quantity = 1`. Named records reuse one hidden food per name and overwrite its variant on every sync. | Its comment says extra nutrients arrive as `custom_nutrients`, but the function does not forward them. Client mapping changes alone would still lose them. |
| Snapshot persistence | `XoTServer/models/food.ts:updateFoodVariantNutrition` supports custom nutrients but keeps the old map when passed `null` (`COALESCE`). `XoTServer/models/foodEntry.ts:createFoodEntry` copies the variant's `custom_nutrients` into the snapshot unless the caller passes an override. | Reuse these paths rather than add one column per micronutrient. Because same-name health records share a variant, a record without magnesium would inherit the previous record's magnesium unless ingestion always passes an explicit map, including `{}`. |
| Totals and presentation | DailySummary's supplement totals, report queries, and web nutrition helpers handle custom nutrients; report pickers use user nutrient definitions and display preferences. `XoTServer/models/reportRepository.ts` computes each custom nutrient as `COALESCE(NULLIF(fe.custom_nutrients->>key, '')::numeric, 0) * quantity / serving_size` for food entries, but uses the tolerant `sf_try_numeric` for supplement snapshots. | Aggregation exists, but a missing value is reported as 0 per entry, so averages and trends already count unknown as zero intake. A non-numeric stored string fails the food-entry cast. |
| Custom nutrient edits | `customNutrientService.updateCustomNutrient` (route `PUT /custom-nutrients/:id`) updates only the definition row and the goal-direction preference key. `custom_nutrients` maps on food variants, diary snapshots, goals, goal presets, and supplements are keyed by name and keep the old name and old unit. | Renaming a nutrient orphans its recorded values; changing its unit silently reinterprets them (100 mg becomes 100 g). A `catalog_id` binding does not fix this on its own, because the stored maps are keyed by name. |
| Permissions | `user_custom_nutrients` uses `create_diary_policy` in `XoTServer/db/rls_policies.sql` and has a unique `(user_id, name)` constraint. The table is not listed in `docs/src/developer/database-security-tiers.md`. | Diary delegates can already create definitions, so provisioning during a delegated import is allowed today by policy; the plan must decide whether that is intended. The unique name constraint already serializes concurrent creation by name. |
| Regression protection | Existing nutrient column coverage tests check selected fixed columns. BLS tests use a small fixture without magnesium. | Current tests can pass while most source nutrient categories remain unsupported. |

The architectural reason is a split between fixed food columns and user-defined nutrient names/units. Adapters implemented the fixed subset, while the broader catalog grew around supplement entry. The code explicitly documents this reason on Android. The evidence establishes the mechanism; it does not establish the original authors' broader intent or the chronology of every decision.

## Proposed design

Retain existing fixed nutrient columns and custom JSON storage. Extend the shared catalog into the source of canonical identity, units, and nutrient relationships. Resolve additional nutrients to each user's existing custom definitions at an authorized write boundary. This keeps current food, diary, goal, supplement, and report consumers compatible while avoiding dozens of new database columns. Automatic import resolution initially operates on the importing user’s private provider foods and consumed snapshots. Never rewrite a shared/public variant using the importing user’s name or unit; broader shared-library resolution requires explicit persisted identity/unit metadata and a separate compatibility test before enabling it.

Use the catalog's existing stable IDs in new import payloads, such as `magnesium`, with explicit source amounts and units. Persist converted values under the user's resolved custom nutrient key, such as `Magnesium` or an existing `Mg`. A label alone must not determine biochemical equivalence. Keep provider I/O and native SDK types in their package adapters; keep identity and conversion behavior in shared.

Reject rename and unit edits of referenced nutrients before adding any binding (Phase 2, step 0). Then add an optional `catalog_id` binding to `user_custom_nutrients`, with uniqueness per user for non-null bindings, as a narrow schema extension. This makes reconciliation deterministic when names change or aliases overlap. Free-text nutrients remain valid with a null binding. Backfill only unambiguous catalog matches with compatible units; leave ambiguous definitions unresolved and report them for review. The backfill itself must not rename existing JSON keys or reinterpret historical amounts; a later, separately implemented owner-authorized conversion may move keys. Shared library keys cannot be rewritten using one user’s definition because other users consume the same values.

Extend the existing catalog rather than replace it; keep `fixedField` as the rule that routes built-in nutrients to their columns, so no adapter creates a second "Vitamin C". Separate canonical nutrient metadata from supplement-only flags and default target metadata where needed. A nutrient can be trackable without having a daily target. Source-specific mapping tables should identify direct fields, catalog nutrients, incompatible forms, blocked components, and unsupported types explicitly.

### Identity and value rules

- Represent mass units explicitly and extend `shared/src/utils/nutrientMatching.ts` rather than adding a second converter: normalize `µg` (U+00B5), `μg` (U+03BC), `mcg`, and `ug`, and convert only compatible units. Return an explicit failure and never store an unconverted value; the fallback in `XoTServer/utils/foodUtils.ts` must change together with the new resolver.
- Treat IU as substance-specific. Only a catalog-declared factor may convert it (vitamin D: 40 IU = 1 µg). Vitamin A and E IU depend on the form and stay unconverted until a documented rule exists.
- Distinguish numeric zero, missing data, and qualified values. BLS numeric zero is real. `TR`, `<LOD`, and `<LOQ` remain qualifiers with no invented numeric amount. Android's current bridge turns unset fields into zero, so those zero values must remain unknown unless the native contract changes. HealthKit zero handling can be source-aware because its records are explicit samples.
- Reject nonfinite and negative intake values, unknown units, unknown catalog IDs, and oversized collections. Avoid rounding small amounts away; use consistent precision through conversion and serialization.
- Map exactly one source component to each target nutrient. Keep retinol, retinol equivalents, retinol activity equivalents, folate/DFE, vitamin E forms, and vitamin K forms distinct; mass conversion alone cannot convert between them, and an unmatched form stays out of scope.
- Never sum several source components into one target nutrient (for example vitamin E forms or vitamin K1 and K2) unless the source documents that total; prefer the source's own total component.
- Changing a user nutrient's unit must convert all dependent stored values and goals through a deliberate operation or be disallowed while values exist. A rename must move the name-keyed values in the same transaction or be disallowed. Today neither happens (see Findings), so this is a precondition, not an audit item.

## Implementation phases

### Phase 1 Inventory and executable coverage contract

1. Extract a checked component manifest from the checksum-pinned BLS workbook: code, official label, unit, basis, form, qualifier behavior, and origin/reference semantics. Do not commit the full source archive. Validate the manifest against all 138 headers.
2. Record the 27-nutrient target set (see Target scope) as a checked shared list with HealthKit identifier, catalog ID, built-in column if any, and unit. Recheck it against the SDK headers and the pinned `@kingstinct/react-native-healthkit` version when either is upgraded.
3. Make a coverage matrix for BLS, HealthKit read, HealthKit write, and Health Connect. Each target nutrient must be mapped or blocked with a reason for each source. Every BLS component must be classified as mapped to a target nutrient, blocked (form or errata), or out of scope; out-of-scope components can share one documented reason. Include verification date and source version. Water stays in the existing hydration path.
4. Verify BLS errata and preserve the vitamin A block until the exact source values and equivalent definition are approved. If adopting corrected data, change the pinned checksum/version and fixtures together.
5. Identify all legacy and v2 search/detail/import endpoints used by web and mobile. Trace response normalization, provider-field preservation, and save validation so the new payload cannot disappear between search and import.

Deliverable: reviewed manifest and behavioral coverage tests for the 27 target nutrients. Implement magnesium first as the end-to-end proof, then the other 20 new nutrients through the same registry; the six built-in columns only need their existing BLS and HealthKit mappings verified.

### Phase 2 Shared contracts and nutrient resolution

0. Initially reject name or unit changes while any referenced values exist, including retained history without a definition. Do not attempt cross-domain rewrites through diary delegation: food library writes are owner-only and supplement writes require medication permissions. Test owner and delegate behavior, concurrent imports, retained snapshots, and collisions with old orphaned JSON keys. A later conversion operation must define shared-library behavior, use one transaction/client and a common locking protocol with imports, and include display preferences and goal-direction preferences as well as every data map. Catalog binding must never change existing units implicitly.
1. Add chloride to `shared/src/nutrients/micronutrientCatalog.ts` and mark the 27 target nutrients with their HealthKit identifiers and source mappings, keeping existing IDs, units, and `fixedField` links. Do not add new catalog entries outside the target set; export the new contracts/helpers from `shared/src/index.ts`.
2. Make conversion failures explicit in `shared/src/utils/nutrientMatching.ts` and remove the unconverted-value fallback from `XoTServer/utils/foodUtils.ts`. Add the Greek `μ` alias and catalog-declared IU factors.
3. Introduce a shared Zod health nutrition observation with quantities `{ catalogId, amount, unit }`, an explicit `partial` or `authoritative` mode, and a bounded list of catalog IDs covered by an authoritative record. Quantities must be unique and within that coverage. Partial observations update only present nutrients; authoritative replacement can clear only covered nutrients. Old clients omitting the observation must preserve existing additional values. HealthKit loose queries always produce partial observations: successful empty reads or revoked permissions do not establish authoritative absence. Explicit deletions require separately verified source tombstones or record revisions. A normalized transport amount must never be converted again as though it were still in its original unit.
4. Add the `catalog_id` migration and shared table schema (`shared/src/schemas/database/UserCustomNutrients.zod.ts`). Add a unique partial index for `(user_id, catalog_id)` and conservative binding backfill. Update custom nutrient API contracts and client types.
5. Extend `customNutrientService` with a resolver that loads definitions once per batch, binds or creates only observed supported nutrients, converts into the user's configured unit, and detects conflicting aliases/units. Use database constraints and transactions for concurrent resolution; the existing unique `(user_id, name)` constraint already guards creation by name. Return structured per-nutrient failures instead of silently dropping values.
6. Separate provisioning from goal seeding and visibility. `ensureCatalogNutrients` passes `defaultTarget: entry.rdi` and the supplement view groups, so reusing it unchanged would seed targets and views as a side effect. Provider observation should create a usable nutrient definition without overwriting existing targets or visibility choices, and without declaring a dietary requirement.
7. Apply resolution at food import/save and health upload write boundaries. Read-only search can expose typed source fields and preview resolved values, but must not create nutrients or edit goals/preferences. Import writes must recompute or validate the preview using the target user's definitions. For verified BLS/health mappings, source-component IDs and form declarations are authoritative; neither label aliases nor client-supplied custom maps may override blocked/out-of-scope dispositions. Keep raw inspection fields separate from the allowlisted fields passed to the matcher. Existing broad supplement aliases are picker conveniences, not proof of biochemical equivalence.

Deliverable: a user with no custom nutrients can import magnesium correctly; an existing `Mg` definition in grams receives converted values without a duplicate definition. Existing supplement behavior and free-text nutrients continue to work.

### Phase 3 Server ingestion and BLS adapter

1. Expand `mapBlsFood` through the verified manifest. Preserve existing direct values and per-100-g edible-mass basis. Expose additional numeric quantities with source units, canonical IDs where known, and qualified/unsupported fields for details. `provider_nutrients` is `Record<string, number>` in `XoTServer/schemas/foodSchemas.ts`, so qualifiers (`TR`, `<LOD`, `<LOQ`) need their own field rather than a sentinel number. Keep origin/reference information accessible through the BLS catalog; persist the dataset reference where history needs it.
2. Keep search mapping pure. In the food import service, resolve supported additional quantities and persist `custom_nutrients` on every variant. Ensure default variant and variants are handled once when they reference the same object. Update `FoodVariantSchema`, normalization, and both import DTO builders to retain new fields.
3. Validate the health payload at the route boundary; replace the `any` parameters of `ingestNutritionFoodEntry` with typed interfaces instead of extending them. Pass the resolved custom map to variant creation, variant update, and `createFoodEntry` snapshot overrides. Always pass an explicit resolved snapshot map because same-name records share one variant and `createFoodEntry` otherwise copies that variant's map into the snapshot. For a new record with no additional quantities, pass `{}`. For a replay, load that specific entry's previous map and apply observation semantics; never read previous values from the mutable shared variant. Clients omitting the new observation preserve that entry's saved values.
4. Keep the existing health-record basis (`quantity = 1`, `serving_size = 1`, consumed amounts as the values). Do not apply BLS per-100-g scaling to them. Preserve current `(user, source, source_id)` upsert semantics and per-record snapshots.
5. Apply partial updates or authoritative replacement only within the explicit covered set. Permission-denied, failed, and successful-but-empty HealthKit loose reads must not clear saved quantities. Reject duplicate IDs and unresolved conversions before mutating a covered set; a conversion failure must not look like a source deletion. Authenticate source provenance server-side; payload mode alone is not evidence of authoritative completeness. Tests cover legacy replay, revoked access, failed queries, explicit zero, authoritative removal, and two same-name records.
6. Ensure nutrient provisioning and food/entry persistence commit consistently, avoiding a stored unrenderable key after setup fails. Retain per-record batch results and retryable failures. Preserve actor and target-user contexts throughout resolution and repository writes.

Deliverable: BLS search → detail → import → stored variant → consumed diary snapshot → daily/range totals retains magnesium. Replaying a health record updates in place without borrowing values from another entry with the same food name.

### Phase 4 HealthKit and Health Connect adapters

1. Derive independent read/write capabilities from the shared identity registry and platform mappings. Stop constraining iOS micronutrients to `HC_NUTRIENT_COLUMNS`, and stop using a write-only identifier list as the loose-read inventory.
2. Extend HealthKit mapping, permissions, loose queries, correlation transformation, permission probing, and typed output. Accept micronutrient-only records. Preserve contained sample UUID exclusion, source-plus-instant grouping, timezone metadata, and own-app writeback exclusion.
3. Request newly supported read permissions on explicit nutrition-sync enable/update. Preserve opt-out and partial access. HealthKit cannot reliably distinguish denied reads from an empty result, so do not label empty data as proof of authorization or as measured zero.
4. Update background delivery for newly relevant identifiers, including micronutrient-only records. The observer in `backgroundDelivery.ts` watches only `DietaryEnergyConsumed`, so those records wait for a foreground or manual sync. Bound concurrent native queries and tolerate individual unavailable types without losing the rest of a batch.
5. Extend writeback to bound custom nutrients using actual configured units, consumed serving scaling, and per-type write authorization. Include the additional values in signatures so a magnesium-only edit triggers writeback. Verify cleanup/retry of old owned samples and feedback-loop guards.
6. Keep food writeback and supplement writeback scope explicit. Food micronutrients must round-trip; existing supplement totals must stay accurate. If supplements are exported to HealthKit, export their dose snapshots separately exactly once, with stable ownership identifiers. Never attach the whole day's supplement amount to every food or write both combined totals and individual items.
7. Extend Android read/write mappings through the same canonical IDs and conversions, preserving the documented unset-as-zero limitation. Confirm installed bridge capabilities before claiming support.

Deliverable: correlation and loose HealthKit magnesium samples ingest correctly, a custom magnesium food writes back in a valid mass unit, and foreground/background/manual sync do not produce duplicates. Android supported nutrients behave consistently.

### Phase 5 Diary reports goals and nutrient visibility

1. Verify existing custom nutrient math for foods, meals, snapshots, supplements, daily summaries, range reports, mobile trends, and exports. Reuse shared resolution/conversion behavior across clients. Preserve existing fixed-field totals.
2. Make observed catalog nutrients discoverable in food details and the nutrient display picker without requiring free-text setup. Preserve explicitly saved visibility choices and Dashboard layouts. Use vitamins and minerals groups with progressive disclosure for the 27 nutrients instead of showing them all by default.
3. Show missing as unknown, distinguish numeric zero, and label totals as recorded intake where coverage is incomplete. Change the report SQL in `XoTServer/models/reportRepository.ts`, which currently coalesces a missing key to 0 per entry, to return a recorded total plus `knownEntryCount` and `eligibleEntryCount` for each nutrient, and use the tolerant `sf_try_numeric` cast for food entries as already done for supplements. A macro-bearing day is not proof that its magnesium data are complete. Count individual consumed food snapshots (including meal components) and countable supplement dose entries, not meal parents or dose quantity. Valid explicit zero is known; absent, qualified, or invalid values are unknown. Return coverage metadata in a dedicated object keyed by catalog ID, never as flattened nutrient keys that the current mobile DTO would interpret as intake. With zero known entries the value is unknown; with some but not all eligible entries it is a partial recorded total. Averages exclude days with no known value and label days with partial coverage; do not describe them as complete average intake. Add a shared response contract and update daily, range, export, and both client consumers together.
4. Offer goals through the existing goal system. Keep existing targets; identify the reference basis for suggested values and allow user selection. Current supplement Daily Values are metadata, not personalized advice or automatic deficiency thresholds.
5. Add English source keys and reviewed German overrides under `localization-overrides/de/` as required by the current root/package guides; apply and check the overlay. Preserve localized number/unit formatting, accessibility, narrow widths, and both themes. Check reporting permissions and read-only family access alongside the owner flow.
6. Preserve a durable identity/unit reservation when deletion retains any history; explicit history purge may remove it only after all references are gone. Later import can reactivate that identity in the reserved unit without overwriting prior visibility choices. Automatic binding/recreation must fail on incompatible historical keys instead of interpreting old values in a new unit. Include orphaned data created by legacy renames/deletes in the conservative backfill audit.
7. Invalidate dependent food search/counts/details, meals, diary, dailySummary/dailyProgress, reports/trends, nutrient definitions, goals, and display preferences when import or binding changes affect them. Use the existing web/mobile invalidation helpers.

Deliverable: the same logged magnesium amount appears in food details, diary totals, reports, and mobile trends; a supplement contribution adds exactly once; unknown values never become a claimed deficiency or a measured zero.

### Phase 6 Existing data recovery and rollout

1. Ship server acceptance and resolver support before clients emit the extended health payload. Keep old clients operational, then enable new adapter collection and visibility.
2. Provide a dry-run, bounded repair operation for provider-managed BLS library variants with a stable BLS code. Resolve against the loaded source version and fill absent supported nutrients; preserve manual edits and existing numeric values. Report proposed changes and unresolved bindings before applying them.
3. Preserve diary history by default. Any historical BLS enrichment must be an explicit, separately reviewable repair using original provider code, serving basis, quantity, and source version. Do not run the existing broad snapshot rewrite against all entries or infer data from a current mutable variant. Deleted/orphaned foods without source identity may be unrecoverable.
4. Add bounded HealthKit/Health Connect replay after new permissions are granted. Reuse stable source IDs so formerly imported records gain micronutrients through upsert, and previously ignored micronutrient-only records can be collected. Cover the selected historical interval rather than relying only on the normal rolling lookback. Respect native history limits and availability.
5. Add counts for mapped, qualified, blocked, unsupported, conversion-failed, and persisted nutrients by source/component. Avoid logging personal food/health content. Track query duration, payload size, batch failure rates, and conversion conflicts.
6. Retain a feature switch for new collection if native issues appear. Disabling collection must not delete saved nutrient data. Keep exact source/image rollback references if deploying, and follow the production revision workflow independently of this plan.

Deliverable: a documented recovery path with dry-run output, safe replay, preserved snapshots, and clearly reported unrecoverable historical data.

## Tests and acceptance criteria

Use synthetic fixtures with explicit units, not invented claims about a specific BLS food's composition. For example, a fixture reporting 100 mg magnesium per 100 g must produce 40 mg from a 40 g serving. A separate 60 mg supplement dose yields a recorded daily total of 100 mg. A HealthKit 0.04 g consumed sample yields 40 mg and is never scaled again. Repeating the same upload leaves one entry and the same total.

| Test group | Required cases |
| --- | --- |
| Coverage | All 27 target nutrients mapped or blocked per source; all 138 BLS component codes classified as mapped, blocked, or out of scope; the target list matches the HealthKit dietary identifiers in the pinned SDK and wrapper. |
| Conversion and identity | mg/g/µg/μg variants, tiny quantities, zero semantics, nonfinite/negative values, incompatible units, ambiguous aliases, blocked edits of referenced nutrients, shared foods, duplicate registration races, distinct biochemical forms, retained-history deletion/recreation. |
| BLS | New-user import without setup, existing nutrient binding, all variants, search/detail/save contract preservation, qualifiers, numeric zero, missing core fields, source-version vitamin A block, one source component per target nutrient, out-of-scope components never persisted. |
| HealthKit | Loose and correlated samples, contained-sample deduplication, magnesium-only intake, partial permissions/query failures, own-app exclusion, repeat sync, source corrections, timezone/day boundaries, background trigger, signature changes and writeback retry. |
| Health Connect | Supported additional masses, unset-zero omission, platform capability gaps, read/write conversion parity, own-app exclusion and repeated upload. |
| Server integration | Real database custom nutrient variant and entry round-trip; two same-name foods with different consumed amounts retain independent snapshots; resync replacement semantics; food deletion preserves diary history. |
| Permissions | Owner, authorized diary delegate, reports-only delegate, unrelated user, and API-key upload; no credential or source identity crossover between users. |

| Recovery | Dry-run performs no writes, repair preserves manual values, repeated repair is idempotent, bounded replay does not duplicate entries, unresolved source/version cases are reported. |

Extend the existing server `blsFoodService`, `healthDataHandlers`, custom nutrient matching/catalog, report custom nutrient, and RLS integration suites.
