## Contracts and staged approach

The app-scope engagement coordinator derives domain-specific effective state, then passes small candidates through a deterministic, clock-injected discretionary policy. Candidate identity, domain record/occurrence identity, prompt identity, and action operation identity stay separate. Medication schedules remain protected, not counted as optional wellbeing prompts. The coordinator reads pending medication requests and reserves their base and repeat times for collision spacing, without modifying those requests. Hydration keeps its existing request owner, but its candidate chain now uses the remaining future slots after meal and movement prompts. A durable, account-scoped local ledger now reserves each optional notification before native scheduling and counts past attempts against the same local-day cap. It deliberately counts an attempted schedule even when OS delivery cannot be observed. All new notifications use a feature-owned identifier namespace; never cancel another family's requests.

The first vertical slice is an opt-in meal-window reminder. Local photo actions count as capture immediately; completion and sync remain independent. A separate opt-in review reminder is proposed only when incomplete photos are locally known and the chosen review time is still ahead; opening it routes to Diary and records nothing. A small iOS widget snapshot shows food-record count and incomplete photos without exposing food names, images, or calorie totals, with account/day scope and freshness. The app-scope coordinator reads the existing nutrition outbox; local saves drive reminder and widget reconciliation. The photo action itself is already durable before network work. The first enabled window is an editable example (11:00–14:00, reminder at 12:30), not an inferred personal routine. Both reminder settings default off. The existing hydration reminder owner was moved from Dashboard to app scope, so its cancellation and day rollover no longer depend on visiting that tab. A plain-water response now uses the durable local action path, and hydration reminder candidates share future slots with meal and movement candidates.

A separate persisted `movementBreak` session is presentation state only. An explicit 2-, 5-, or 10-minute start requests a Live Activity on iOS. The session is scoped to the active account/server, adopted on relaunch only when the matching ActivityKit instance exists, and never recreated after dismissal. `staleDate` marks suspended-app content stale; app foreground/active-JS expiry reconciliation sends the actual end request. The timer never records movement. There is no all-day activity or push update infrastructure. An opt-in daily movement invitation can open this timer at a user-chosen time. It shares the nutrition discretionary cap and collision policy, stops when a break has already started that day, and does not create a movement record.

## Dependency and blocker report

- Ordinary medication notification actions still call the API directly. Planned supplement responses now use a scoped server operation ID and the nutrition action outbox, with server-side occurrence validation. The new server migration and RLS applied to a local isolated PostgreSQL test database; physical replay remains outstanding.
- Water intake has server aggregation semantics and a distinct existing scheduler. Plain-water and container operations use the existing ledger `source_id` index and the established mobile action outbox. The itemized log exposes each operation ID so local water can be reconciled with the server after a lost response without counting a replay twice. Container presses also have a separate immutable server receipt and one transaction for the water row, optional linked food row, and daily aggregate. The mobile container button, linked quick-add presets, and Watch bridge enqueue the action before network work and reuse its operation ID on retry. A queued container drink appears as a count and anchors reminders immediately; its volume remains unknown until the server resolves its water credit.
- The Watch bridge handles check-ins and selected quick logs, but no universal typed response contract. Extension actions must be introduced through its existing transport.
- Widget reloads and local notification delivery are OS-controlled. A successfully written snapshot/request does not prove a widget was viewed or a notification delivered.
- The current nutrition state counts grouped logged meals, standalone food records, and photos. It does not claim these are all eating events or infer that a missing record means a missed meal.
- Nutrition is capped at one selected capture window plus one separately enabled later review prompt; movement adds at most one opt-in daily invitation. The future water chain takes the remaining slots of a three-prompt plan and observes 20-minute spacing around optional prompts and pending medication doses. The persisted ledger enforces three scheduled attempts per account/local day across these reminder owners, including attempts earlier in the day; a future slot is released only after confirmed native cancellation with more than two minutes remaining. This is conservative scheduled-attempt accounting, not proof of OS delivery. Previously scheduled requests from older builds are migrated on reconciliation; they cannot be counted before the upgraded app runs. A newly scheduled medication request can be observed on the next app-scope reconciliation tick.
- The development Expo config lacks `ios.appleTeamId`; the simulator target built without signing, while physical-device provisioning remains unverified for this branch.
- ActivityKit has a maintained `expo-widgets` route and an existing workout Live Activity, so a separate bounded wellbeing activity is feasible without editing generated native projects. Entitlement/build/device checks are still required.

## Disable, upgrade, and rollback

Turning the meal or movement reminder off causes its app-scope reconciler to cancel only its own `engagement:nutrition:` or `engagement:movement:` requests; the stored photo/food records remain. Finishing a break ends only the session and its Live Activity. The medication owner remains separate; the hydration owner uses its own notification namespace under the app-scope coordinator. The new preference keys use the existing shallow default merge, so older preference blobs load with the reminders off. The session and widget snapshots are versioned; unreadable sessions surface an error rather than being treated as movement records.

Before downgrading to a build without this feature, turn the meal reminder off in the new build while it is running so its owned requests are cancelled. An old build does not know that namespace and cannot clean it up. A downgrade ignores the new local session and widget snapshot. The planned-supplement action table is a separate forward-only server migration; do not remove it while queued clients may replay their operation IDs.

The next slice is to validate scoped Watch actions, the 250 ml action, widget account switch, and shared reminder budget on the paired devices, and to review how older unscoped Watch captures can be safely attributed or discarded. Ordinary medication notification buttons still use their direct online API path; planned supplement buttons now use the separate schedule-occurrence offline contract. Watch action expansion follows those contracts rather than inventing another transport.
