## Implementation stages

1. **Phone goal correctness.** Fix activity localization and optional skip discovery. Reuse activity planning's revisioned resolver. No planned activity may become a completed workout just by tapping a goal.
2. **Dashboard overview.** Share centered icon headings and category projection. The card lists categories, while the breakdown retains individual goals. Existing logging and navigation destinations stay available.
3. **Watch localization.** Translate shipped static copy, accessibility and state messages through the existing native resource pipeline. Provider/user names stay literal. Validate the native tables rather than trusting source-key existence.
4. **Watch daily goals.** Extend the existing account-scoped context and WatchConnectivity queue with bounded current-day items. Allow explicit confirmation of completion habits and meal state, where no measurement or workout evidence is invented. Counts, health questionnaires, workouts and intake schedules that require richer information explain that they need the phone. Reuse phone APIs and existing Watch persistence. Record a durable attempt receipt before non-idempotent phone writes; a lost acknowledgement must never replay an action over a later undo. Uncertain outcomes require refresh/reconfirmation, not blind resubmission. Never label queued work complete.
5. **Review, correction and handoff.** Run focused behavioral tests, affected package validation, native build and a bounded simulator review. Correct observed failures, commit in staged changes, and record remaining physical-device checks explicitly.

## Plan review

The stages use existing routes, identity guards, APIs, progress projection and native transport. No migrations, new scheduler, new backend, feature-gate activation or goal-policy changes are needed. Optional activity is distinct from skipped activity. Unknown data is not zero. Watch actions require a matching active account and the snapshot's local day. Late or unsupported confirmations fail safely. German text is required in the same change. Skip the blanket backend suite as requested; run targeted tests if server/shared behavior changes.
