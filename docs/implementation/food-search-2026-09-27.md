# Food search retrieval and ranking

## Verified causes and correction

- BLS lookup used a whole-query `ILIKE` expression. A name such as `Reis, gekocht` could match `reis gekocht` only by accident, and reversed word order could not match. Search now builds parameterized identity-token and full-token PostgreSQL text queries, ranks before pagination, and uses a GIN index (`20260926220000_bls4_token_search_index.sql`). BLS still requires numeric source energy and core macros; qualified or absent values are not converted to zero.
- The combined mobile and web search formerly took the first two rows from each provider in round-robin order. It now ranks all retrieved candidates together by food identity, preparation compatibility, exact/complete name coverage, and then small favorite/source tie-breakers. Different records with the same name remain distinct; repeated source IDs and barcodes are deduplicated after ranking.
- Saved-food SQL now puts exact food names ahead of broader matches before pagination. Mobile saved-food and meal hooks suppress previous-query placeholder rows while a new term is debouncing.
- The public Open Food Facts Search-a-licious request appended a nutrient query expression and requested only a small page. It now sends normalized plain text, puts identity before an initial preparation word (`gekochter Reis` → `reis gekocht`), filters unusable nutrition locally, and lets the combined view evaluate a bounded 100-result page. It retains the existing single bulk hydration, timeouts, rate limits, cache, and custom-provider fallback.
- Search rows now form one ranked list by default, with optional provider sections below. Alternatives with missing or conflicting preparation information carry an explicit note. Provider attribution, images, nutrition basis, barcode selection, favorites, and portions remain in the existing flows. The selected-food screen shows the selected serving and provider variants; the web edit/add form exposes available variants.
- Search query keys now include provider, query, locale, relevant display options, and a ranking version. Authentication changes already clear the app query caches, keeping account data separate.

## Fixture outcomes

The deterministic fixture checks retrieval-independent ranking. `tomate` and `tomate roh` place raw tomato first; celeriac is excluded. `reis gekocht` and `gekochter reis` place cooked rice first; cooked meat is excluded. `reis trocken` favors dry rice. `apfel`, `äpfel`, and `aepfel` find apple; `tomat` matches tomato; `Ei` finds egg. `tomate frito freshona` favors the branded product. An exact barcode wins. A saved sauce marked favorite does not outrank raw tomato for a raw query. These results are fixture observations, not claims about the live provider catalogues.

## Operational verification still required

Read-only verification on 2026-09-27 found that the running deployment database has `public.bls4_foods` and one active, public BLS provider, but **zero catalogue rows**. The BLS table migration is installed; the new token-search index migration is not yet deployed. Consequently `tomat`, `apfel`, and `reis` have zero live BLS matches because the catalogue is empty, rather than because the current provider is disabled. The checks cannot establish whether an earlier import was attempted. No production data was changed.

The official BLS 4.0 archive is available from the [Max Rubner-Institut download page](https://www.blsdb.de/download). A local read-only `import_bls4.py --check` confirmed its pinned SHA-256, all 7,140 records, and 7,090 records with numeric energy and all three core macros. It includes `Tomate roh` (`G561100`), `Apfel roh` (`F110100`), `Reis poliert, gekocht` (`C352032`), and `Reis unpoliert, gekocht` (`C351032`). After a fresh matched backup, the verified archive was imported atomically on 2026-09-27. The deployment catalogue now contains all 7,140 foods, including 7,090 with numeric energy and all three core macros. Apply the new index migration with the search release. Then recheck `tomat`, `apfel`, `reis`, qualified nutrient exclusions, pagination, and the language passed by the client. The pending search code distinguishes an empty catalogue (503), matches with no eligible core nutrients (422), and a genuine empty match (200); these responses have not been verified against the live deployment.

The BLS SQL and index have mock-query tests but still need a real PostgreSQL smoke test. An anonymous, read-only Search-a-licious check with the same German language and 100-candidate settings retrieved an exact `Tomate` in the first two results for `tomate`, a `Tomate` at upstream position 17 for `tomate roh`, and cooked rice at positions 1–2 for `reis gekocht`. The upstream `tomate roh` page began with unrelated celeriac and meat; the local identity gate removes those before display. A dry chickpea product branded “Reis” initially ranked first for `reis trocken`, and a dehydrated tomato ranked near the top for `tomate roh`. The final name-identity and form corrections demote both. The read-only requests completed in roughly 0.1–0.5 seconds, excluding bulk hydration and the app network path, so they are **not** a measurement of time-to-first-useful-result in the app. The returned `Tomate` lacks an explicit raw label and is correctly treated as a broader alternative until a verified raw record is available. A separate device check should measure displayed top-three recall, partial provider timeout, and cached/offline behavior. Server-local BLS is not phone-offline data. None of the changes alter production data or logged nutrient snapshots.

## Reference and next improvements

The local OpenNutriTracker checkout informed exact-match protection, token overlap, stable cross-source ranking, and delayed selection of a short result list. This implementation keeps distinct same-name nutrient records and reports provider errors instead of adopting the reference's weaker merge/error behavior. Next, measure live top-three recall and latency for the fixture queries; review any observed German aliases/typos; then tune candidate limits or preparation detection only where those measurements show a gap.
