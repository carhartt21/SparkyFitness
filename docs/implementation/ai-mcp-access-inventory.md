## Work still required before an external read-only pilot

- The delegated exercise-diary tool now defaults to a 20-entry page and accepts a 50-entry maximum. Each entry carries its own sets; the response includes `total_count`, `has_more`, and `next_offset`. The full chatbot retains its prior unpaged output shape. A formatter-shortened page recalculates the cursor from entries actually returned. Set counts are not independently capped, so a large single entry can still trigger an output truncation warning.
- The read-only evidence block now reports `output_truncation: reported` when the shared formatter omits fetched records or cuts an oversized result; `not_reported` means only that no formatter warning appeared. This does not establish account-history completeness.
- Audit field-specific units, per-record provenance, completeness, and stale or unsynced device data with synthetic and live results. The common evidence context makes these limitations explicit, but cannot fill missing source fields or establish completeness. Per-call bounds do not prevent repeated pagination across calls.
- `stats_summary` reads the previous comparison window as well as the requested window; its evidence context now reports both periods. Decide whether that derived comparison remains in the external pilot scope.
- Verify a revoked read-only key, a hidden or multiplexed mutation attempt, admin escalation, cross-owner data access, and protected REST denial against a running instance. The synthetic tests prove narrower code paths and guard order only.
- Pick a specific client, server, account, and permitted data scope with the owner; record the credential lifecycle and run a traceable read-only review. Do not place keys, personal data, or provider responses in the repository.
- Keep supplement timing in recommendation/review mode. No dose, product, schedule, or diary mutation is authorized by this stage; the owner must approve any later action policy separately.
