# Remote engagement delivery and assistant access

Remote engagement is opt-in. The account owns a revisioned settings row; a phone registers its Expo push token only after notification permission. The token is encrypted at rest, its digest prevents two accounts sharing one active recipient, and the owner can disable remote delivery from mobile or web Settings. Initial activation must happen on the phone so it can remove locally scheduled optional alerts before remote delivery begins; web and MCP can then change reminder kinds and quiet hours while the app is closed. Local discretionary reminders pause while remote delivery owns them. Medication and rest timer notifications stay local.

The five server-side prompts are hydration, meal capture, meal photo review, movement break, and mobility. The planner uses the account timezone and current diary evidence, quiet hours, a three-per-day cap, and twenty-minute spacing. It does not infer missing logging as a confirmed health deficit. A five-minute cron claims due occurrences before sending; uncertain Expo sends are not retried because Expo has no idempotency key. A second cron checks push receipts. Snooze and Skip use immutable operation IDs so mobile retries and MCP actions cannot duplicate the response.

To enable OAuth MCP, migrate the database and set `SPARKY_FITNESS_MCP_OAUTH_RESOURCE` to the exact public HTTPS URL `/mcp/chatgpt` (for example `https://fitness.example.com/mcp/chatgpt`). Keep `BETTER_AUTH_URL` on the same public origin that serves the web login and `/api/auth`; the reverse proxy must forward the OAuth `/.well-known/oauth-*` and `/.well-known/openid-configuration` discovery URLs, `/api/auth/*`, and `/mcp/chatgpt`. The existing API-key `/mcp` endpoint remains available. `EXPO_PUSH_ACCESS_TOKEN` is optional unless Expo push security is enabled for the project.

The ChatGPT endpoint requires `mcp:read`; write tools require `mcp:write`. Better Auth verifies token signature, issuer, audience, and scope. The endpoint also checks the current owner consent on each request so disconnecting a client takes effect immediately even for a signed access token that has not expired. Web Settings revokes both access and refresh grants. The database owner handles OAuth tables; application-role RLS has no access to them. Do not expose access tokens or push tokens in logs.

Before production rollout, verify a signed-in OAuth authorization round trip, disconnect while a client token is still valid, an actual push on a closed iPhone, Snooze/Skip from the notification, and the fasting/mobility Live Activities on an installed iOS build. The repository checks and synthetic database tests do not substitute for those device checks.
