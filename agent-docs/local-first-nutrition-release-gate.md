A signed standalone test build also installed and launched on an iPhone 17 Pro running iOS 27.2 beta. The updated favorite-cache build installed and launched after the device reconnected to Xcode.

## Device acceptance still required

An iPhone 17 Pro running iOS 27.2 beta is paired over USB with Developer Mode enabled. The owner verified the isolated test server through Tailscale in iPhone Safari. The server is bound only to the Mac's Tailscale address and remains unreachable on its public network interface. Do not point a branch build at the existing production v1.7.2 API; it lacks the new endpoints.

The first physical-device build failed with Xcode error 65 because no Apple account was signed in. The owner signed in, but the default development bundle IDs belonged to another team. A clean local prebuild with temporary `EXPO_DEV_BUNDLE_IDENTIFIER=de.ilmtech.sparkyfitness.localfirsttest`, matching `IOS_APP_GROUP_DEV`, and team `4V6HSJQ4JP` then built and installed successfully on the iPhone. These identifiers are local build settings; no tracked product identifiers changed. The one-origin HTTP exception is enabled only by explicit test-build environment variables; production remains HTTPS-only. The later direct-launch test used Airplane Mode and a stopped API; an earlier airplane-mode attempt had ambiguous Tailscale connectivity.

Use synthetic data only. Record the exact build commit and server commit, iOS version, device model, and test time. Do not record personal meal names or photos in test evidence.

1. Build/install the development app, sign in to the matching test server while online, cache one synthetic favorite and meal type, and confirm the direct `sparkyfitnessmobile://meal-photo` route opens the camera.
2. Enable airplane mode. Log the cached favorite and capture a synthetic meal photo without AI or calories. Confirm both appear immediately, with the photo marked incomplete and the offline summary labeled device-only.
3. Force quit and reopen offline. Confirm the same action IDs, original timestamps, nutrient snapshot, and durable photo remain. Complete the existing photo manually; confirm its capture ID and image remain, and the incomplete count falls.
4. Restore connectivity. Wait for reconciliation; confirm each logical action appears once in the diary and database. Deliberately replay each create/complete operation ID against the test API and confirm no extra rows. Force quit and reopen again.
5. Test an invalid/expired session and server switch separately: pending actions must remain in their original account/server partition. Confirm no data is sent to the wrong account.

## Device findings and outstanding blockers

- Widget action from the Home Screen passed with the API stopped, including offline restart and later reconciliation. Widget cold launch from a force-quit state also opened the camera. Direct camera cold launch in Airplane Mode and with the API stopped passed separately.
- An early airplane-mode run had ambiguous connectivity because Tailscale still answered pings. The owner later disconnected Tailscale and confirmed Safari could no longer load the synthetic backend. The isolated API was also stopped for a definitive server-unavailable run.
- A definite server-outage run followed: the isolated test API was stopped and its database held five captures. The iPhone saved a new synthetic photo, showed it as incomplete, and retained it and its original time through a force-quit and reopen while the API remained unavailable. The database stayed at five rows throughout. After the API restarted, the capture synchronized once: the database increased to six rows, the new row retained its 12:05:32 local capture instant and one image, and the owner saw one diary row. An authenticated retry using the same capture ID returned the same record with the count still six. Another iPhone restart kept the photo visible once with its original time.
- The owner completed that same capture on the phone with synthetic `TEST MEAL` values (200 kcal, 20 g protein, 10 g carbohydrate, 5 g fat). The server retained the original capture ID and 12:05:32 timestamp, one image, and exactly one linked food entry with those values. An authenticated completion retry returned the existing result; the linked food count stayed one. After another force-quit/reopen, the owner still saw one completed entry with the image and no duplicate incomplete row.
- The first favorite device attempt failed because nullable optional nutrient fields from the API prevented the local favorite cache from validating. The app now omits unknown optional values while preserving known zero. After installing the corrected build, the Diary quick button remained available during a server outage and the two deliberate taps passed the offline persistence and duplicate-safe sync checks. Food Search favorites still depend on the server and its favorite row opens food details; this is distinct from the Diary quick action.
- The iPhone's development provisioning profile had to be validated online after an offline reinstall before iOS would launch the newly signed build. With a working USB connection, `devicectl` later cold-launched the app in Airplane Mode and the camera opened directly.
- The camera entry screen previously remained at “Saving meal photo…” on a repeat attempt. Presenting the system camera during the native-stack modal's opening transition was the likely race. The screen now waits for `transitionEnd`, with a cold-launch fallback. Four focused tests pass. On the updated iPhone build, the owner opened, canceled, and reopened the Diary camera successfully in one app session.
- Food Search completion now passed the physical-device path, including the normal diary row and photo viewer after restart. It currently supports one reviewed food snapshot per capture; multi-food completion is a separate future design.
- An initial rapid save immediately after sign-in failed once before retry succeeded. The account-identity priming fix has unit coverage and is in the installed build, but a true fresh-sign-in device retest remains outstanding. This mobile build has no sign-out control; server reconfiguration is not an equivalent test.
- The Mac's active network address is public, so a plain LAN HTTP listener would expose test credentials. The branch supports `SPARKY_FITNESS_SERVER_BIND_HOST` for restricted development binds; the default bind behavior for container deployments is unchanged. The owner verified the existing Tailscale route from iPhone Safari.
- The selected development backend is not yet deployed with this branch. Production should remain on its pinned release until a restorable production backup, matching server rollout, and owner-approved cutover procedure are ready.
- AI completion of an existing photo, photo deletion and local-file cleanup, local widget numeric snapshots, direct favorite widget/App Intent actions, and Watch nutrition actions remain unimplemented. This branch cannot be declared to meet those later-stage acceptance tests.
- The current completion contract supports one reviewed food snapshot per capture. A multi-food photo requires a separate schema/API design.

## Rollout order

1. Take and restore-test a backup of the target environment; preserve the previous image digest and schema-compatible rollback plan.
2. Apply the three migrations and matching API, then run auth/RLS/idempotency smoke tests on the target server.
3. Install a development mobile build on the iPhone and execute the synthetic offline tests above against that matching API.
