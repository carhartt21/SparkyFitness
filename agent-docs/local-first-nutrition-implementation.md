# Local-first nutrition implementation note — 2026-09-23

Baseline: clean `main` at `3c84e8007fb4f2541c58238ec71a2dcbb7d458a4`; production remains pinned to upstream v1.7.2. This branch is development work only and must not be deployed until migrations and mobile compatibility are validated.

Current flow: mobile FoodSearchScreen hands a selected food to `useAddFoodEntry`; that hook may first create a catalog food/variant, then calls `POST /api/food-entries/` via `foodEntriesApi`. The server route authorizes `diary` access, the service passes a snapshot to `models/foodEntry.ts`, and PostgreSQL generates the entry UUID. Manual requests have no request identity. Provider imports already use the separate `(user_id, source, source_id)` upsert; that contract updates provider snapshots and must not be reused for immutable manual actions. Logged meals have a parent `food_entry_meals` row and component rows, so a future meal operation needs its own atomic parent-level key.

Action model: one versioned `PendingNutritionAction` with UUID `clientOperationId`, owner/server-config identity, occurrence timestamp and day/time, immutable payload snapshot, status (`pending`, `syncing`, `attentionRequired`, `synced`), retry metadata and optional server ID. Its first type is `logFoodEntry`; later types are distinct rather than overloaded. Nutrition values may be absent/null but are never invented as zero. Capture succeeds only after durable local write.

Server contract: optional `client_operation_id` UUID on `food_entries`, unique per `(user_id, client_operation_id)` when present. The first request inserts a normal food snapshot; repeated requests return that existing row, without updating its nutrition or date. A precheck supports retries after a catalog item has disappeared; the unique index and conflict recovery make concurrent or response-lost retries safe. Legacy clients omit the field and keep current behavior. RLS and diary permission checks stay in force. A different payload with the same operation ID is a caller error to be detected before broad rollout; the ID is not an edit API.

Persistence: use AsyncStorage for a small versioned outbox, partitioned by active server configuration and user identity. Secrets remain in SecureStore. Serialize mutations to avoid whole-document read/write races. Store durable camera files in Expo FileSystem application documents, with action records referencing them; never persist picker cache URIs. On sign-out or server switch, retain old partitions but do not replay them in the new identity.

Reconciliation: one coordinator at a time, bounded attempts/backoff, foreground/startup/connectivity triggers and explicit retry. Treat uncertain HTTP outcomes as retryable only once server idempotency is available. Keep local action until a response with server identity is durably recorded; then invalidate diary query caches. Auth failures pause without deleting, permanent validation errors require attention. Logs contain operation IDs and error classes, not meal names or photos.

Diary projection: merge pending actions with remote entries by `client_operation_id` or mapped server ID; use the operation UUID as stable local row identity and original occurrence time. Show pending/attention state quietly. Remove the local overlay only after matching server data is visible, avoiding both disappearance and double count. Keep normal online editing/deleting unchanged until those actions use the same model.

Photo model: a separate incomplete nutrition occurrence with stable ID, capturedAt and consumedAt, optional category/notes, durable image attachments, null/unknown nutrients and completion state. Save locally before upload/AI. Completion updates that same occurrence, preserving image and capture time. This requires server schema and API work beyond `food_entries`, whose current RLS requires a food/meal reference and whose summaries assume a consumable item; do not fake a zero-calorie food row.

Native boundary: existing WidgetKit snapshots use ExtensionStorage/app group and URL deep links; Watch uses WatchConnectivity and a phone bridge. Native actions should enqueue the same operation envelope in a shared app-group store or hand it safely to the React Native app. No widget/Watch direct server writes. Existing calorie/macro widgets and Watch features remain intact.

Stage gates: finish and validate server idempotency before changing offline UI; commit each working stage. No HealthIntel import or production deployment in this branch. The repository guides still mention old `docs/content/...` paths; current docs are under `docs/src/...`.
