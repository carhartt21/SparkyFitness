# X on Track progression identity

The four unchanged supplied raster references are in `references/`. The SVG masters in `../assets/brand/` and the application PNGs are generated from `shared/src/brand/progressionX.geometry.json` by `node scripts/generate-progression-x.mjs`. This JSON is the single source for the mark's geometry, segment order, color stops, baseline colors, and paths used by both progress components. The standalone full and empty drafts determine the outline and crossing; the dashboard mockups guide surfaces and hierarchy. Their sample dates, values, tagline, goals, and promotions are not product data.

The canonical mark has five overlapping paths inside a 320 × 320 viewbox: four rounded outline segments and one filled, tapered diagonal sweep. The sweep is drawn last so its crossing remains continuous. The source drafts have small raster asymmetries, so this vector fixes one geometry for full, empty, partial, and unknown states. Gradients stay anchored to the full paths; only the progress mask's measured arc length changes. The generated static SVG adds a separate, subtle glow layer and border for large brand placements. Dynamic components omit that decorative glow to stay crisp at small sizes.

The SVG master was refined against both standalone drafts. Its rounded frame now uses the references' inset and shorter height, the empty state has a neutral dimensional slate treatment, and the full state uses a warm lower-left border, localized green wash, brighter lower-right path, and separate soft and wide bloom layers. The path silhouette and center sweep stay identical in every state. `review/progression-x-full-comparison.png` and `review/progression-x-empty-comparison.png` place the source raster on the left and the generated SVG on the right at equal size. The original JPEGs contain photographic glow and texture, so their pixels cannot be reproduced exactly by scalable vector shapes; the canonical geometry and visually meaningful color relationships are preserved.

`BrandMark` is static and fully lit. `ProgressTrackX` takes a single number or unknown value, a label, and an unknown label. It is used for completed/planned sets in live workout headers on iOS and web. Zero keeps the whole graphite track visible; unknown dims that track and uses explicit unknown text. Invalid non-finite input is unknown; finite out-of-range input is clamped to 0–100. The web component interpolates from its current rendered value on retargeting; the mobile component stops its running animation and continues from its stopped value. Reduced-motion settings skip interpolation. Corrections may decrease the value.

The energy ring remains a conventional ring because calorie allowance is not a measure where “more is better.” No aggregate health score drives the static header mark. Live-workout progress uses actual completed sets divided by planned sets; no planned sets is unknown. The color spectrum describes distance along the logo's path, not health quality.

The mobile dashboard keeps its existing date, food, scan, hydration, workout, and recent-entry flows. The web keeps its existing route permissions, search destination, account controls, logging dialogs, widgets, and movable dashboard. The sidebar appears at 1280 px and above; smaller tablet layouts keep horizontal navigation and narrow web keeps the mobile navigation. Diary widget thresholds account for the sidebar's 248 px width, keeping two summary cards at 1280 px and three at 1440 px. Quick actions use real existing flows. Web hydration no longer substitutes an invented 1,920 ml goal when none loads. Visible brand copy and web metadata use the new core line, “Whatever your X, keep it on track.”

Synthetic simulator screenshots are in `review/`; names indicate width/theme/scenario. They are not personal account data. The 390 and 430 captures were compared with `references/progress_x_mockup_dashboard.jpg`: the centered energy summary, quick actions, accent colors, metric hierarchy, and dark surfaces are present. Deliberate departures include restrained glow, a date-first header consistent with the prior approved header direction, the existing scrollable stacked hydration and exercise cards, and the existing bottom navigation destinations. The mockup's calorie arithmetic, suggested goal checks, motivational copy, and promotions were not copied.

Web screenshots requiring authenticated data are unverified because no disposable preview account is available. A physical-device installation, Watch/widget rendering, and a native release build are also unverified for this branch. The simulator captures verify layout rendering, not persistence or backend integrations. The new light mark asset was visually inspected, but the post-change light dashboard capture remains unverified because the preview harness rendered the dark theme for that scenario.

### Center-crossing correction

The subsequent logo review exposed a missing diagonal between the left junction and upper center, visible round-cap seams, and an overlapping crescent where the sweep met the lower-right loop. The canonical paths now restore that diagonal and join the sweep to the loop at matching boundaries. Explicit butt caps at the joining segments are consumed by both progress adapters and the SVG generator. All static exports were regenerated. The latest comparisons are `review/progression-x-full-corrected.png` and `review/progression-x-empty-corrected.png` (reference left, SVG right). The earlier comparison is retained. These correct structural defects; raster bloom and surface highlights still differ.

Validation for this correction: nine focused web/mobile brand tests passed, both app TypeScript checks passed, SVG XML validation and whitespace checks passed. The dynamic component changes were not rechecked on a physical device.

## Screen alignment pass (2026-09-28)

Scope: align the remaining mobile references (`progress_x_diary.png`, `01_food_search.png`, `02_food_item_details.png`, `03_settings.png`, `04_insights.png`) and the web dashboard reference, without removing existing functionality. Owner decisions taken before implementation: tabs become Home · Diary · + · Insights · More, with More holding the former Library and Settings moving to the upper-left corner; build Insights from real data; web adds a logging streak and a Today's Focus checklist only (no greeting, global search, quote, or Pro upsell); Settings gets a restyle and an account card, without regrouping or search.

### Mobile

- **Navigation.** Tab routes are `Dashboard` (label Home, house icon), `Diary`, `Add`, `Insights`, `More`. The route name `Dashboard` is unchanged so deep links, widgets and launch actions keep working. `More` renders the existing `LibraryScreen`. `Settings` is now a root-stack route with a back header. Every content tab exposes it in the upper-left corner: `SettingsHeaderButton` on custom headers, and on native headers either `settingsAction` in `setNativeHeaderDatePickerOptions` (Home, Diary) or the tab stack's left header item (Insights, More). All former `('Tabs', { screen: 'Settings' })` calls now open the root route; onboarding's "Later" resets to Tabs → Settings so Back works. The custom tab bar shows an underline under the active tab.
- **Insights** (`InsightsScreen`, `utils/insights.ts`). 7d/30d/90d range. Calories: average per _logged_ day, difference from today's goal, and the existing `NutrientBarChart` with its goal line. Macronutrients: energy share (4/4/9 kcal/g) in the existing `MacroCompositionRing`, with average grams. Weight trend: existing `WeightLineChart`, latest value and change within the range, plus a Log weight action. Key insight: "You logged food on N of the last M days." Missing days are unknown, never zero. The reference's 1Y range is omitted because the existing charts and trend hooks are built for 7/30/90 days; a 365-bar daily chart would be unreadable without weekly aggregation.
- **Diary.** The summary is a bordered card with four rings (Calories, Carbs, Protein, Fat) showing "of goal"; a missing goal omits the denominator and fill. The server-computed remaining/over text, the expand toggle (fiber and custom nutrients), and the TDEE projection are unchanged. Meal cards use 16-pt corners, a subtle border, per-meal accent icons, right-aligned kcal and a raised Add food button. Tapping the header for the breakdown, drag-to-move and bulk selection are untouched. Collapsible meal sections from the reference were not added because the header tap already opens the meal breakdown.
- **Food search.** Local results show brand · serving on one line with a trailing add affordance. It is decorative; the row still opens the entry screen, and no one-tap logging was added. The landing list ends with a Scan barcode card that opens the existing scanner. The existing All/Recent/Favorites control is kept; the reference's "My Foods" filter already exists as the ownership menu.
- **Food details.** Calories, protein, carbs and fat are tinted, color-coded tiles in the reference order. The portion slider, fixed 50/100/150/200 g chips and the second "Add to Diary" button were not added: the stepper, unit picker and "Enter amount in grams" already cover portions, and variant quantities are not always grams.
- **Settings.** An account card (profile name or "Your account", initials, connected server host → Server Settings) sits above the unchanged groups. Row icons use semantic colors on tinted tiles (`utils/colorTint.ts`, shared with the food-detail tiles). No email, plan, or invented profile data is shown.

### Web

- `TodaysFocusCard` replaces the "Configured goals" panel and keeps its Goals link ("Edit goals"). Items appear only for configured goals: energy within goal (`calorieBalance.eaten` ≤ goal and > 0), protein goal reached, water goal reached (only when the daily summary loaded), and food logged for the day. There is no steps item because no steps goal exists.
- `LoggingStreakBadge` in the page header counts consecutive days with logged food ending at the selected day, from the existing mini nutrition-trend endpoint over 90 days (shown as "90+" at the cap). An unlogged selected day does not break the streak. The badge is hidden while loading, on error, or at zero.
- Eight pre-existing English locale keys used by the prior identity commit were added so the translation-coverage test passes. `index.html` was reformatted (it failed `format:check` at HEAD).

## Neon visual pass and quick add (2026-09-28, mobile)

Owner direction: match the mobile references as closely as possible (widgets, surface and item colors, neon glow, shared card and button design), starting with the Dashboard; Settings moves to the Dashboard's upper-right corner; add quick add from the food search list through a serving bottom sheet, and serving quick amounts on the food details page. The web is deferred. This section supersedes the earlier notes in this file that the search-row "+" was decorative and that fixed 50/100/150/200 g chips were not added.

### Design system

- Tokens (`SparkyFitnessMobile/global.css`): the dark theme was re-sampled from the references (background `#020c10`, surfaces `#08181e` / `#10242b`, borders `#17313a`, accent `#14e89a`), macros now follow the reference (protein red, carbs yellow, fat green, fiber violet), hydration cyan and exercise yellow. New `--color-neon-*` tokens exist in every theme; AMOLED keeps its black canvas; light mode keeps cream surfaces with darker hues of the same colors.
- Primitives in `src/components/ui/`: `glow.ts`, `GlowCard`, `NeonButton`, `ActionTile`, `IconBadge`, `ScreenBackground`. Dark themes use RN 0.86 `boxShadow` glows and `experimental_backgroundImage` gradients (no native dependency); light mode uses soft shadows. `ui/Button` primary, `SegmentedControl`, `SettingsRowGroup`, `CreateTile` and the Dashboard/Diary cards adopt the same 16-point bordered card and capsule controls.

### Screens

- **Dashboard:** logo + "X on Track" + localized tagline with Settings upper-right (native iOS header: right item); shared `DateBar`; Calories card with a 270° red→yellow→green `EnergyGauge`, remaining balance and consumed / burned / goal rows that open Diary, exercise review and Calorie settings, plus Edit goal; four neon action tiles; Macronutrients and Hydration tile side by side (cups, percentage, − / + amount); a Drinks card only for sync states, several containers or presets; Exercise summary (kcal burned | total time, goals as "of X"); "Today at a glance" chips for logged meals, workout and water. The exercise card's own Log button was dropped because the Log exercise tile opens the same flow.
- **Diary:** `TabScreenHeader` + `DateBar`; the ring summary leads the page and is now shown by default for new installs (existing saved preferences are kept); meal cards glow in their meal color; quick nutrition uses `NeonButton`s.
- **Insights, More, Settings, Food search, Food details:** glow cards, capsule filters, ambient background, circular icon badges, glass search field and cards.

### Quick add

- `QuickAddFoodSheet` (`src/components/foodSearch/`) opens from a local food row's "+" in diary logging mode (not in multi-select, photo capture or picker modes). It lists the food's stored servings, 0.5/1/1.5/2× amount presets (`utils/quickAddServings.ts`), the meal (route meal or app default, changeable) and live calories/macros, and logs through `convertDraftToPayload` + `useAddFoodEntry` (full cache invalidation, error toast; the sheet stays open on failure). "More options" opens the full entry screen. It uses the overlay `sheetContainer` so it renders above the modal search screen.
- Food details show the same presets under the amount stepper; tapping sets the amount (logging remains the explicit Add action). Saved meals do not show presets.
